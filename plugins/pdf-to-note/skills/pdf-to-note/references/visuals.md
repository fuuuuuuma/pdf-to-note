# 画像制作とPDFスライド

## noteの寸法を先に確認する

公式ヘルプ「登録画像の推奨サイズ一覧」を開いて、記事の見出し画像と本文画像に適用される現在の条件を確認する：

<https://www.help-note.com/hc/ja/articles/360000231642-%E7%99%BB%E9%8C%B2%E7%94%BB%E5%83%8F%E3%81%AE%E6%8E%A8%E5%A5%A8%E3%82%B5%E3%82%A4%E3%82%BA%E4%B8%80%E8%A6%A7>

2026-10-09の制作では、見出し画像は1280×670、10MB以下を確認した。この値を恒久仕様として扱わず、次回も確認する。選んだ寸法・容量上限・確認日・URLを案件の `request-contract.json` に保存する。

`sumnessy-team` のYouTube用3840×2160をnoteにそのまま適用しない。縮小QCもnoteの比率を保つ。生成サービスが厳密寸法を出せない場合は近い比率で生成し、原本を残して許可されたリサイズで書き出す。「指定サイズでの生成」と「生成原本からリサイズした書き出し」を区別する。構図を変えるクロップや文字修正は画像生成編集で行う。

## 参考画像を観察してから設計する

1. 利用者が指定し、実行環境で利用できるサムネイル制作Skillがあれば、そのSkillの実ファイルと該当リファレンスを読む。作成者の端末に固有の絶対パスや、存在を確認していない参考素材集・履歴を前提にしない。追加Skillが利用できない場合は、このファイルに書かれた基準と利用者が提供した資料を使う。
2. 登録された保存サムネの全コンタクトシートを確認して記録する。その後、同じテーマに近い候補2〜4枚を原寸で確認する。前回の記憶だけで済ませない。
3. 保存済みの参考画像とデザイン観察を使い、テーマ・文字量・階層・色・背景・余白を今回のサムネに合わせる。新しい競合画像の調査は、今回のユーザー指定がある場合、または利用できる画像資料がなく構図確認が必要な場合だけ行う。画像の目視に絞り、競合noteの本文やBrainで記事の書き方を再学習しない。新規調査をした場合は観察URLと範囲を記録する。
4. `design-decision.json` に、参考のどの要素をどう応用するかを書く。クリック率や売上を検証していなければ、優劣を成果として断定しない。

借用するのは情報の見せ方。競合の人物・ロゴ・顔・文言を複製しない。主題と読者の変化を短いコピーにし、太い日本語文字と十分な余白で優先順位を作る。確認できない書体名を断定しない。

## 生成と品質確認

- 利用中の `imagegen` Skillとツール仕様を確認する。生成・編集は画像生成ツールを使う。既に承認されたバックエンドと利用条件を優先し、未承認の有料API利用を足さない。
- **初回・修正とも完成1案だけを作る。** 初回はA、修正はR1など1件で管理し、品質のための内部修正は別の提案数に数えない。確定文言・素材・配置条件を守る。後続の案数指定があれば優先する。
- `batch.json` を使う制作手順では `count_override` を `{"count": 1, "evidence": "pdf-to-note Skillの標準は1案。今回の案数指定があればそれを優先。"}` として保存する。参照元の検証スクリプトを使う際も、案数とnote用canvas寸法を正しく設定し、plan / deliveryの対応する検証を行う。検証を通すために架空の画像・QC・採用記録を作らない。
- 完全な生成プロンプトを保存する。JSONプロンプト形式を使う場合は、その生成ツールが対応する制約項目を使い、確定文言や保持対象を明記して原寸と縮小で実画像QCを行う。
- 日本語の誤字、書体と文字の太さ、縦横比、配色、フチ・影、輪郭・影を含む文字同士の接触、余白、ノイズ、指定素材の保持を完成画像で確認する。数字・記号・改行が確定していれば厳密に照合する。人物の元写真を直接配置する指定や正式ロゴの保持条件を優先する。原寸とnoteの比率を保った縮小プレビューで読みやすさを確認する。
- 内部修正後の画像を再確認する。メタデータの合格やリサイズだけで品質確認完了としない。
- `original.png`、`delivery.png`、縮小プレビュー、`prompt.json`、`qc.md` をその1案について保存する。修正は版番号を付け、指定外の変更を戻さない。品質確認を通った完成画像をnoteに適用し、設計理由と適用した版を記録する。ユーザー採用済みとは偽らない。

## 本文スライドを選ぶ基準

優先する図版：対比、2軸、流れ、工程、一覧、構造の変化、実例の配置関係。文字だけのスライドを無理に挿入しない。説明文の直後、または比較を扱う段落の近くに配置する。図版が別のテーマへの移行を遮らないよう確認する。

同じ意味の図を連続させない。記事全体に説明上必要な図が分散するよう選び、何文字ごと・何枚という固定ルールにしない。前後の文章だけで図の意味が理解できることを確認する。PDFの内容を図版で代用して本文を薄くしない。

原本からの描画には `scripts/prepare_pdf.py` を使える。全ページの抽出に続けて図版を追加するときは、出力先を別の新しいフォルダにする。スクリプトは既存フォルダを上書きしない。

```bash
python3 <SKILL_ROOT>/scripts/prepare_pdf.py --pdf '<PDF>' --output '<新しいフォルダ>' --pages '<今回選んだページ番号>' --scale-to 1600
python3 <SKILL_ROOT>/scripts/prepare_pdf.py --pdf '<PDF>' --output '<別の新しいフォルダ>' --crop '<ページ:x:y:幅:高さ>' --scale-to 1600
```

座標は今回のPDFを画像で確認して決める。過去案件の選定ページや座標を使い回さない。表のみの切り取りでも、数値の条件・注釈・主体が抜けないか確認する。

配置台帳の各項目には次を保存する：source_page、image_path、sha256、crop（あれば）、reason、heading、paragraph_anchor、upload_url（アップロード後）、loaded、確認日時。URLを確認する前にアップロード成功を推測しない。
